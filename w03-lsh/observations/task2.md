# Task 2 — Observation

## 작은 데이터에서는 전체 비교가 더 빨랐다

Core i5-11400H, RAM 약 15.74 GiB(16 GB급), Windows, Python 3.11.9에서 측정했다. 최초 단회 결과만으로 역전 구간을 단정하지 않도록 세 크기를 각각 5회 재측정했다.

| 문서 수 | 전체 비교 중앙값 (범위), 초 | LSH 중앙값 (범위), 초 | LSH가 빨랐던 횟수 |
|---:|---:|---:|---:|
| 500 | 0.901 (0.855~1.096) | 1.991 (1.784~2.241) | 0/5 |
| 750 | 2.389 (2.045~2.657) | 2.065 (1.913~2.437) | 5/5 |
| 1,000 | 4.363 (3.751~4.667) | 2.753 (2.549~2.809) | 5/5 |

500개에서는 5회 모두 전체 비교가 빨랐고, 750개와 1,000개에서는 5회 모두 LSH가 빨랐다. 따라서 이번 고정 데이터와 계측 조건에서 관측한 역전 구간은 500~750개다. 이는 그 사이의 정확한 역전값이나 다른 실행 환경에 대한 보장이 아니다. 750개는 두 방법의 전체 측정 범위가 겹치며, 실행별 차이는 약 0.06~0.32초로 여전히 작다.

LSH는 후보 비교 전에 해시 계산과 캐시 생성, 서명 갱신, 밴드별 버킷 구성과 중복 제거를 수행한다. 작은 데이터에서는 이 준비 비용이 절약한 비교 비용보다 크다는 해석과 결과가 부합한다. 세부 단계별 시간은 따로 측정하지 않았으므로 각 비용의 비중까지 확인한 것은 아니다.

## 전체 비교 시간은 대체로 이차 증가했다

기존 크기 확장 실험에서 문서 수를 250→500→1,000→2,000→4,000으로 늘렸을 때 전체 비교 시간 배율은 4.49, 4.43, 4.15, 3.98배였다. 비교 횟수 n(n-1)/2와 함께 대체로 이차 증가를 뒷받침한다. 이 배율은 기존 단회 측정값끼리 계산한 것으로, 새 반복 측정의 중앙값과 섞어 계산하지 않았다.

## 약 1분은 측정 종료 기준이다

기존 4,000개 단독 측정에서 전체 비교는 59.44초, LSH는 4.43초였다. 과제에서 예로 든 약 1분의 대기 기준에 도달한 크기로 4,000개를 기록하고 크기 확장을 종료했다. 이는 사용자가 실제로 불편함을 느꼈다는 보고나 컴퓨터의 처리 한계가 아니다. 시간 제한 초과, 메모리 부족, 실행 실패는 발생하지 않았다.

4,000개에서 추가 Python 메모리 최고값은 전체 비교 22,312 bytes, LSH 29,714,016 bytes(약 28.34 MiB)였다. 미리 생성한 입력 데이터와 전체 프로세스 RAM은 제외된 값이다. 전체 비교는 추가 할당이 작고, LSH는 캐시·서명·버킷을 위한 공간을 사용한다.

## 결과를 해석할 때의 한계

2,120개 이후에는 유사 문서를 추가로 심지 않고 무작위 문서만 늘렸으므로 데이터 크기와 함께 유사 문서의 비율도 달라진다. 전체 비교 횟수는 여전히 n(n-1)/2이지만, LSH 후보 수와 실행 시간은 이 데이터 구성의 영향을 받는다. 따라서 대규모 LSH 결과를 유사 문서 비율이 일정한 데이터의 성능 곡선으로 일반화할 수 없다. 이번 역전 재측정은 모두 2,120개 이하의 동일한 고정 시드 문서 목록의 앞부분을 사용했다.

기존 측정과 별도로 500·750·1,000개를 각각 5회 측정했다. 크기 순서를 섞었으며 각 측정 안에서는 제공 코드대로 전체 비교 후 LSH를 실행했다. 별도 워밍업은 하지 않았고, 동시에 다른 벤치마크를 실행하지 않았다. Codex와 사용자 앱의 백그라운드 부하는 통제하지 않았다. 두 방법 모두 tracemalloc을 켰으며 이 계측 오버헤드가 포함된다. 같은 크기에서는 같은 데이터를 사용했다. 아래 범위는 최솟값~최댓값이며 신뢰구간은 아니다.

최초 4,000개 측정은 다른 검증 실행과 겹쳐 제외했고 기존 단독 재측정값을 유지했다. 반복 측정은 시간 변동만 확인하며 여러 무작위 데이터에 대한 일반화 실험은 아니다. 모든 시간은 계측을 켠 조건에 한정된다.
