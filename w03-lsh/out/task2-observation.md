# Task 2 — Observation

## 실행 환경과 속도 역전

Core i5-11400H, RAM 약 15.74 GiB(16 GB급), Windows, Python 3.11.9에서 250~4,000개 문서를 측정했다. Codex가 실행 중이었고 다른 사용자 앱은 통제하지 않았다. 500개에서 전체 비교는 0.81초, LSH는 1.75초였지만 750개에서는 각각 2.08초, 2.00초였다. 이번 측정의 역전 구간은 500~750개이며, 750개에서의 차이가 작으므로 정확한 경계는 반복 측정에 따라 변할 수 있다.

LSH는 실제 비교 전에 해시 계산, 서명 생성, 밴드별 버킷 구성과 후보 중복 제거를 수행한다. 작은 데이터에서는 이 준비 비용이 절약되는 비교 비용보다 커서 전체 비교가 더 빨랐다.

## 이차 증가 확인

문서 수가 250→500→1,000→2,000→4,000으로 두 배씩 늘 때 전체 비교 시간은 각각 4.49, 4.43, 4.15, 3.98배가 되었다. 비교 횟수 n(n-1)/2와 함께 보면 대체로 이차 증가를 뒷받침한다. 단회 측정의 변동과 계측 비용이 있으므로 모든 비율이 정확히 네 배라고 주장하지 않는다.

## 부담이 커진 크기와 메모리

4,000개에서 전체 비교가 59.44초로 약 1분 걸려 시간 부담이 커지는 지점으로 기록했다. LSH는 4.43초였다. 메모리 부족이나 실행 실패는 없었으며 먼저 부담이 된 자원은 시간이었다.

같은 크기에서 추가 Python 메모리 최고값은 전체 비교 22,312 bytes, LSH 29,714,016 bytes(약 28.34 MiB)였다. 이는 tracemalloc이 find 실행 중 추적한 할당이며, 미리 만든 입력 데이터와 전체 프로세스 RAM을 포함하지 않는다. LSH는 캐시·서명·버킷 때문에 추가 메모리를 사용한다.

## 측정의 한계

원본 생성기는 2,120개까지만 만들기 때문에 Task 2에서 고정 시드로 무작위 문서를 추가했다. bench.py는 수정하지 않았다. 최초 4,000개 측정은 다른 검증 실행과 겹쳐 제외하고 단독 재측정값을 사용했다. tracemalloc의 시간 오버헤드가 포함되어 있어 계측하지 않은 벤치마크 시간과 직접 비교해서는 안 된다.
