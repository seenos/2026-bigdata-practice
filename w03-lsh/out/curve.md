# Task 2 — 실행 시간과 메모리 측정

## 측정 환경과 방법

- CPU: 11th Gen Intel Core i5-11400H @ 2.70GHz
- RAM: 16 GB급 (16905064448 bytes, 약 15.74 GiB)
- Windows, Python 3.11.9. 측정 중 Codex가 실행 중이었으며 다른 사용자 앱은 종료하거나 통제하지 않았다.
- 제공된 timed 함수를 사용했다. 시간에는 tracemalloc 계측 오버헤드가 포함되고, 입력 생성은 포함되지 않는다.
- 메모리는 find 호출 중 파이썬 할당의 최고값이다. 이미 생성한 docs와 전체 프로세스 메모리·운영체제 메모리는 포함하지 않는다.
- 원본 bench.build()는 2,120개만 생성하므로, 원본을 수정하지 않고 Task 2에서 추가 문서를 고정 시드 247로 생성했다. 어휘 크기 5,000, 문서당 60개 원소를 유지하며 실제 문서 수를 assert로 확인한다. 추가 문서는 무작위 문서이며 유사 문서를 추가로 심지 않았다.
- LSH: 120개 해시, 30개 밴드, 밴드당 4개 값. 공통 원소의 해시값은 호출 내부 캐시로 재사용한다. 캐시 생성도 시간·메모리에 포함된다.
- 최초 4,000개 측정(62.17초)은 별도 벤치마크와 일부 겹쳐 원시 JSON에 note로 표시하고 아래 표에서는 제외했다. 단독 재측정값을 사용한다.

## 기존 크기 확장 실험의 시간 곡선 (A3)

| 실제 문서 수 n | 전체 비교 시간(s) | LSH 시간(s) | 전체 비교 횟수 | LSH 비교 횟수 |
|---:|---:|---:|---:|---:|
| 250 | 0.1811 | 1.4651 | 31,125 | 1 |
| 500 | 0.8129 | 1.7503 | 124,750 | 7 |
| 750 | 2.0778 | 1.9965 | 280,875 | 14 |
| 1,000 | 3.6011 | 2.0391 | 499,500 | 26 |
| 2,000 | 14.9266 | 2.9964 | 1,999,000 | 109 |
| 4,000 | 59.4428 | 4.4305 | 7,998,000 | 163 |

250개에서 4,000개까지 16배 범위를 측정했으며, 750개를 포함해 서로 다른 크기 6개를 측정했다.

## 두 배 증가 시 시간 비율 (A4)

| 크기 변화 | 전체 비교 시간 배율 |
|---|---:|
| 250 → 500 | 4.49배 |
| 500 → 1000 | 4.43배 |
| 1000 → 2000 | 4.15배 |
| 2000 → 4000 | 3.98배 |

비교 횟수는 정확히 n(n-1)/2이며, 시간도 대체로 4배 부근으로 증가했다. 작은 크기에서 4배보다 조금 큰 비율은 한 번씩 측정한 값의 변동과 실행 환경·계측 비용의 영향을 받을 수 있다. 모든 값이 정확히 4배라는 주장은 하지 않는다.

## 부담이 커진 크기와 메모리 (A2, A5)

기존 4,000개 단독 측정에서 전체 비교는 59.44초, LSH는 4.43초였다. 과제에서 예로 든 약 1분의 대기 기준에 도달한 크기로 4,000개를 기록하고 크기 확장을 종료했다. 이는 사용자가 실제로 불편함을 느꼈다는 보고나 컴퓨터의 처리 한계가 아니다. 시간 제한 초과, 메모리 부족, 실행 실패는 발생하지 않았다.

| 4,000개에서의 추가 Python 메모리 최고값 | bytes | MiB |
|---|---:|---:|
| 전체 비교 | 22,312 | 0.0213 |
| LSH | 29,714,016 | 28.3375 |

전체 비교는 입력 집합을 재사용하므로 추가 할당이 작다. LSH는 해시 캐시, 서명, 버킷을 보관하므로 추가 메모리가 크다. 이 수치를 전체 프로그램의 RAM 사용량으로 해석하면 안 된다.

## 역전 지점과 작은 데이터에서의 비용 (A7, A8)

500개에서는 5회 모두 전체 비교가 빨랐고, 750개와 1,000개에서는 5회 모두 LSH가 빨랐다. 따라서 이번 고정 데이터와 계측 조건에서 관측한 역전 구간은 500개에서 750개 사이이다. 이는 그 사이의 정확한 역전값이나 다른 실행 환경에 대한 보장이 아니다. 750개에서는 두 방법의 전체 측정 범위가 겹치며, 실행별 차이는 약 0.06초에서 0.32초로 여전히 작다.

LSH는 비교 전에 원소별 120개 해시 계산과 캐시 생성, 문서별 최솟값 서명 생성, 30개 밴드의 버킷 구성 및 후보 중복 제거를 수행한다. 작은 n에서는 이 준비 비용이 전체 비교로 절약하는 시간보다 커서 느리다. n이 커지면 전체 비교의 이차 증가가 이 비용을 앞지른다.

## 역전 구간 반복 측정

기존 측정과 별도로 500·750·1,000개를 각각 5회 측정했다. 크기 순서를 섞었으며 각 측정 안에서는 제공 코드대로 전체 비교 후 LSH를 실행했다. 별도 워밍업은 하지 않았고, 동시에 다른 벤치마크를 실행하지 않았다. Codex와 사용자 앱의 백그라운드 부하는 통제하지 않았다. 두 방법 모두 tracemalloc을 켰으며 이 계측 오버헤드가 포함된다. 같은 크기에서는 같은 데이터를 사용했다. 아래 범위는 최솟값부터 최댓값까지이며 신뢰구간은 아니다.

| 문서 수 | 전체 비교 중앙값 (범위), 초 | LSH 중앙값 (범위), 초 | LSH가 빨랐던 횟수 |
|---:|---:|---:|---:|
| 500 | 0.901 (0.855–1.096) | 1.991 (1.784–2.241) | 0/5 |
| 750 | 2.389 (2.045–2.657) | 2.065 (1.913–2.437) | 5/5 |
| 1,000 | 4.363 (3.751–4.667) | 2.753 (2.549–2.809) | 5/5 |

원시 JSON의 `batch=crossover_repeat_5`인 15개 행만 집계했다. 기존 7개 측정값은 보존했으며 위의 크기 확장 표와 배율 계산은 기존 결과다. machine의 available_ram_bytes는 최초 환경 기록이며 반복 측정 당시의 가용 RAM 실측값이 아니다.

## 데이터 구성에 따른 해석 범위

전체 비교는 모든 문서 쌍을 검사하지만, LSH는 후보로 선택되지 않은 유사 문서 쌍을 놓칠 수 있다. 이 구현은 후보 쌍의 실제 자카드 유사도를 확인해 최종 결과를 결정한다. 따라서 이번 실행 시간 비교가 두 방법의 결과나 재현율이 완전히 같음을 의미하지는 않는다. Task 2에서는 크기별 재현율을 별도로 측정하지 않았다.

2,120개 이후에는 유사 문서를 추가로 심지 않고 무작위 문서만 늘렸으므로 데이터 크기와 함께 유사 문서의 비율도 달라진다. 전체 비교 횟수는 여전히 n(n-1)/2이지만, LSH 후보 수와 실행 시간은 이 데이터 구성의 영향을 받는다. 따라서 대규모 LSH 결과를 유사 문서 비율이 일정한 데이터의 성능 곡선으로 일반화할 수 없다. 이번 역전 재측정은 모두 2,120개 이하의 동일한 고정 시드 문서 목록의 앞부분을 사용했다.
