# Task 3 — 같은 PageRank를 희소하게 계산하기

## 예상과 구현

노드가 n개이고 간선이 E개인 그래프에서 기준 구현은 n×n 행렬을 만들고 매 반복마다 모든 행렬 위치를 검사한다. 대부분의 위치가 0이어도 검사 비용이 발생한다. 입력이 이미 인접 리스트이므로 이를 그대로 순회하면 각 반복을 O(n+E)에 처리할 수 있을 것으로 예상했다.

YourPageRank는 입력 그래프를 재사용하고 현재·다음 중요도 벡터만 보관한다. 간선별 실수 가중치도 별도로 저장하지 않고 출발 노드의 중요도를 나가는 링크 수로 나눠 전달한다. 모든 링크 목적지가 그래프 키에 있고 중복 간선이 없는 제공 그래프의 전제를 따른다.

## 측정 조건과 결과

공식 bench.py를 수정하지 않고 1,200개 노드·5,877개 간선, beta=0.85, tol=1e-10, 최대 100회로 실행했다. Core i5-11400H, RAM 약 15.74 GiB, Windows, Python 3.11.9 환경이며 Codex 외 앱 부하는 통제하지 않았다. 기준 구현과 개선 구현의 초기값과 종료 조건은 같다.

| 항목 | 기준 행렬 구현 | 개선 구현 |
|---|---:|---:|
| 실행 시간(공식 출력의 반올림값) | 1.01초 | 0.02초 |
| 보고한 실수 저장 개수 | 1,440,000 | 2,416 |
| 중요도 합계 | 1.000000 | 1.000000 |
| 기준 대비 노드별 최대 절대 차이 | — | 5.55e-17 |

공식 실행의 내부 정밀도 시간으로 계산한 속도 향상은 48.4배, 저장 개수 감소는 약 596.0배로 strong 조건을 충족했다. 반올림한 표의 시간끼리 나누면 출력 배율과 다를 수 있다. 이는 한 번의 벤치마크 결과이며 모든 환경에서 같은 속도 향상을 보장하지 않는다. 이후 전체 테스트에서 정확성과 저장 개수 조건도 다시 통과했다.

## 메모리를 어떻게 셌는가?

개선 구현은 두 벡터의 최대 2n개 실수 값에 beta·tol, 나눗셈 결과, 누적값, 차이 계산 등 스칼라와 임시 값에 대한 보수적인 여유 16개를 더해 2n+16을 보고한다. 따라서 1,200개에서는 2,416개다. 이는 실제 할당을 추적한 정확한 실수 객체 개수가 아니라 과소계산을 피한 상한 추정이다. 값 공유로 실제 객체 수가 더 작을 수도 있다.

입력 인접 리스트는 O(n+E) 크기이며 문자열·컨테이너를 포함한다. 개선 알고리즘이 추가하는 실수 저장량은 O(n)이다. 공식 지표는 실수 개수이므로 사전·리스트·문자열의 바이트나 Python 전체 RAM 사용량은 아니다. 기준 memory_floats()도 n²의 행렬 항목만 보고하고 벡터·스칼라를 추가하지 않으므로, 596배는 제공 지표의 비교이며 프로세스 메모리를 596배 줄였다는 뜻은 아니다.

## 순간 이동에 왜 큰 행렬이 필요하지 않은가?

순간 이동은 모든 노드에 같은 `(1-beta)/n`을 더하는 것이다. 노드 n개를 한 번 순회하면 되며, 모든 노드 쌍에 대한 n²개 항목을 저장하거나 계산할 필요가 없다. dead end의 중요도 합 D도 한 번 계산해 각 노드에 beta*D/n을 더하면 된다. 모든 노드를 만지는 O(n) 연산과 모든 노드 쌍을 만지는 O(n²) 연산은 다르다.

## 정확도와 한계

공식 최대 차이 5.55e-17은 요구치 1e-9보다 충분히 작다. 기준 구현은 도착 노드별로 항을 더하고, 개선 구현은 dead end 합을 먼저 모은 뒤 출발 노드별 기여를 누적하므로 실수 덧셈 순서와 나눗셈·곱셈 순서가 달라진다. 두 구현은 같은 수학적 갱신을 수행하지만 부동소수점 반올림 때문에 비트 단위로 완전히 같을 필요는 없다.

추가로 SIMPLE·DEAD_END·SPIDER_TRAP·단일 dead end·2노드 순환·모든 노드가 dead end인 그래프에 beta=0·0.85·0.99와 tol=1e-6·1e-10을 적용한 36개 조합을 비교했다. 최대 차이는 약 6.66e-16이었고 모두 1e-9 이내였다. 빈 그래프는 빈 결과를 반환하는 것도 확인했다. 이 검증이 모든 가능한 그래프를 포괄하는 것은 아니다.
