# Task 3 — Observation

## 같은 저장 예산에서 해시 수를 늘렸다

기본 필터는 해시 1개를 사용한다. Bloom filter의 근사 오탐률은 `p(k) = (1 - exp(-kn/m))^k`이다. `x = kn/m`으로 놓으면 `ln p = (m/n) x ln(1-exp(-x))`이고, 미분한 식이 0이 되는 조건은 `ln(1-exp(-x)) + x/(exp(x)-1) = 0`이다. 최적점은 `x=ln 2`이므로 `k=(m/n)ln 2`이다.

항목당 10비트를 온전히 비트 배열에 쓰면 최적 k는 약 6.93이므로 정수 7을 선택한다. 연속적인 k에서의 최적 근사 오탐률은 `(1/2)^(10 ln 2)`, 약 0.8193%이다. 이는 일반적인 Bloom filter 모델에서의 최적값이며 모든 종류의 필터에 대한 절대적인 하한이라는 뜻은 아니다.

## 실제 메모리 계산

이 구현은 비트를 bytearray에 압축하고 __slots__로 인스턴스 속성 사전을 없앴다. memory_bits()는 필터 인스턴스, bytearray의 헤더와 버퍼, 시드 bytes 객체를 모두 합산한다. 입력 항목이나 해시별 결과를 별도 캐시에 저장하지 않는다.

| 보관하는 객체 | Python 3.11.9에서 측정한 bytes |
|---|---:|
| 필터 인스턴스 | 48 |
| bytearray 전체 | 9,916 |
| 시드 bytes | 36 |
| 합계 | 10,000 |

합계는 80,000비트이며 bytearray 내부의 실제 비트 데이터는 9,859 bytes, 즉 78,872비트이다. 이 유효 m에서 최적 k는 약 6.83으로 여전히 7이고, k=7의 예측 오탐률은 약 0.8774%이다. 인스턴스가 지속적으로 보관하는 모든 객체를 계산했으며 공유 코드·Python 런타임·호출 중 임시 해시 작업 공간을 포함한 프로세스 최고 메모리를 뜻하지는 않는다.

제공된 NaiveFilter는 bytearray(n_bits)를 할당하면서 memory_bits()에서 n_bits를 반환한다. 따라서 기본 구현의 실제 버퍼는 80,000 bytes인데 보고값은 80,000 bits이다. 제공 bench.py와 NaiveFilter는 수정하지 않았고, 아래 비교는 공식 검증의 예산·점수 체계를 따르되 우리 구현의 실제 보관 공간은 별도로 확인했다. 두 구현의 실제 Python 메모리가 같다고 주장하지 않는다.

## 측정 결과

고정 시드 246, 삽입 8,000개, 미삽입 조회 200,000개에서 다음 결과를 얻었다.

| 방법 | 오탐 수 | 오탐률 | 미탐 수 |
|---|---:|---:|---:|
| 기본 필터 | 19,023 | 9.5115% | 0 |
| 구현 필터 | 1,712 | 0.8560% | 0 |

오탐률을 약 91.0% 줄였고 0.9% 이하인 strong 조건을 충족했다. 삽입 시 켠 비트를 지우지 않으며 같은 해시 위치를 조회하므로 삽입 항목에 대한 미탐이 없다.

실측 0.8560%는 전체 80,000비트를 배열에 쓰는 이상적인 최적 근사값 0.8193%보다 약 0.0367%p 높다. 객체 저장 비용을 반영한 예측값 0.8774%와도 가깝다. 고정된 조회 표본과 실제 해시의 결과이므로 예측값과 정확히 일치할 필요는 없으며, 이번 실측값을 모든 데이터에 대한 보장으로 해석하지 않는다.

## 삽입 수를 모르면?

이 구현의 해시 7개는 과제의 8,000개 삽입 조건에 맞춘 값이다. 생성자에 항목 수가 전달되지는 않으므로 임의의 삽입 수에 자동 최적화되는 필터는 아니다.

삽입 수를 적게 예상하면 배열이 포화되어 오탐률이 커지고, 많이 예상해 미리 크게 할당하면 메모리를 낭비한다. 예산 확장이 가능하다면 점유율을 관찰하고 새 Bloom filter를 추가하는 방식으로 용량을 늘리되 전체 오탐률도 관리할 수 있다. 고정 예산과 전체 이력 보존을 모두 유지해야 한다면 무한히 늘어나는 고유 항목에 대해 낮은 오탐률을 계속 보장할 수 없다. 최근 구간만 유지하는 방식은 가능하지만 과거 항목을 잊기 때문에 이번 과제의 전체 이력에 대한 미탐 금지 조건과는 다른 계약이다.
