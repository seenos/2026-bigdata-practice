# Task 2 — Observation

Core i5-11400H, RAM 약 15.74 GiB, Windows, Python 3.11.9에서 측정했다. Codex가 실행 중이었고 다른 사용자 앱은 통제하지 않았다. 두 방법 모두 입력 생성과 tracemalloc의 계측 비용을 포함한다.

## 메모리를 절약한 대신 정확도와 시간이 달라졌다

10,000·40,000·160,000·640,000·6,400,000개 입력에서 정확한 set과 FM을 각각 실행했다. 입력이 640배 늘자 set의 최고 메모리는 603.541배, FM은 1.001배였다. 끝점 기반 증가 지수는 각각 0.991과 0.000으로, 이 데이터에서 set은 대체로 선형이고 FM은 거의 일정했다. set의 공간은 정확히는 고유 항목 수와 항목 길이에 달려 있다.

FM의 추정/실제 비율은 입력 크기 순서대로 1.115배, 1.466배, 1.219배, 1.847배, 0.892배였다. 크기가 커질수록 정확해진다는 단조로운 추세는 없었다. 메모리 절약이 정확한 결과를 보장하는 것은 아니다. 이번 Python 구현의 FM은 64개 해시 출력을 처리하므로 시간은 set보다 더 걸렸다.

## 시간 기준에서 측정을 끝냈다

정확한 집계만 추가로 크기를 늘려 실행했고 16,000,000개에서 66.98초, 최고 메모리 703.77 MB를 기록했다. 약 60초의 대기를 실험 종료 기준으로 삼았으므로 시간 기준에 먼저 도달한 것으로 기록한다. 메모리 고갈이나 처리 불가능한 최대 크기를 찾은 것은 아니다. 1,600만 개의 FM은 실행 중단으로 완료 결과가 없고 긴 측정 시간 때문에 재실행하지 않았다. 이 크기는 set의 추가 실험으로만 사용하며, 640만 개까지의 다섯 크기 비교 실험과 구분한다.

## 방문자 수에 2배 오차가 허용될까?

서비스 이용 규모가 수천 명인지 수십만 명인지 파악하는 용도에는 유용할 수 있다. 반면 고유 방문자 수를 기준으로 요금을 정산하거나 5% 증가 여부를 판단하는 용도에는 부적절하다. 과제의 2배 오차 기준은 모든 스트림에 대한 보장이 아니다.
