# Task 2 — 메모리 한계 측정

## 환경과 측정 방법

- CPU: 11th Gen Intel(R) Core(TM) i5-11400H @ 2.70GHz, RAM 16,905,064,448 bytes (약 15.74 GiB).
- Windows-10-10.0.26200-SP0, Python 3.11.9.
- Codex 실행 중. 다른 사용자 앱은 종료하거나 통제하지 않았다. 벤치마크는 순차 실행했다.
- 고정 시드 246, 기본 distinct_ratio=0.4인 제공 스트림 생성기를 사용했다. n은 전체 입력 수이며 고유 항목 수가 아니다. 정확한 고유 항목 수는 set으로 직접 계산했다.
- 시간과 메모리는 tracemalloc을 켠 상태에서 측정했다. 이번 주차는 입력 생성도 계측에 포함된다. 메모리는 Python 할당의 최고값이며 전체 프로세스 RAM이 아니다.
- FM은 64개 해시, 그룹 크기 8의 중앙값들을 평균한다. 같은 시드의 새 생성기로 같은 입력을 다시 생성한다. 두 방법이 같은 생성기를 이어서 소비하지 않는다.
- 각 크기당 1회 측정이며, 작은 차이의 통계적 유의성을 판단하는 실험은 아니다. 가용 RAM은 실행 묶음 시작 시점의 스냅샷이다.

640만 개의 paired 결과는 처음 네 크기와 다른 날에 측정했다. 기존 exact_only 결과는 보존하며, 비교 표에는 두 방법이 함께 완료된 paired 결과만 사용한다. 640만 개의 set 시간은 기존 26.30초와 재측정 55.60초로 차이가 있으므로 실행 환경에 따른 시간 변동에 유의해야 한다.

## 다섯 크기의 비교 실험 (A1, A3, A5)

| 전체 입력 n | 실제 고유 수 | set 시간(s) | set 메모리(MB) | FM 시간(s) | FM 메모리(bytes) | FM 추정값 | 추정/실제 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10,000 | 3,675 | 0.035 | 0.343120 | 4.160 | 5,007 | 4,096 | 1.115 |
| 40,000 | 14,665 | 0.140 | 1.368255 | 17.430 | 5,072 | 21,504 | 1.466 |
| 160,000 | 58,799 | 0.725 | 5.500925 | 87.553 | 5,072 | 71,680 | 1.219 |
| 640,000 | 235,071 | 3.152 | 22.159352 | 326.662 | 5,073 | 434,176 | 1.847 |
| 6,400,000 | 2,349,909 | 55.598 | 207.086882 | 5718.847 | 5,010 | 2,097,152 | 0.892 |

MB는 1,000,000 bytes이다. 전체 입력 범위는 640배로 최소 16배 조건을 충족한다. FM의 정확도 비율은 크기에 따라 변하며, 입력이 커질수록 반드시 좋아지거나 나빠진다는 추세는 이 측정만으로 확인할 수 없다. 아래 추가 경계 탐색과 이 다섯 크기의 비교 실험은 구분한다.

## 메모리 증가율 (A4)

n이 640배 늘었을 때 set의 최고 메모리는 603.541배, FM은 1.001배였다. 양 끝점에서 계산한 지수 log(메모리 배율)/log(n 배율)는 set 0.991, FM 0.000이다. 이는 끝점의 경험적 증가율이지 회귀분석이나 복잡도 증명은 아니다.

이 실험에서 고유 항목 수도 n과 함께 늘기 때문에 set의 메모리는 대체로 선형 증가했다. 일반적으로는 전체 입력 수보다 고유 항목 수와 항목 길이에 좌우된다. FM은 고정 개수의 최대값만 유지하므로 거의 일정했다. 해시 수와 해시 폭을 고정한 구현에서의 관찰이며, 문자열 길이와 임시 객체 때문에 측정값이 완전히 같을 필요는 없다.

이 Python 구현의 FM은 메모리를 절약했지만 시간은 더 오래 걸렸다. 항목마다 64개 해시 출력을 처리하고 tracemalloc의 계측 비용도 포함되므로 메모리 절약을 속도 향상으로 해석할 수 없다.

## 정확한 집계의 추가 경계 탐색 (A2)

비교 실험과 별도로 정확한 집계만 추가 실행했다. 측정 종료 기준은 정확한 집계의 약 60초 대기 시간으로 정했다.

| 전체 입력 n | 실제 고유 수 | set 시간(s) | set 메모리(MB) |
|---:|---:|---:|---:|
| 6,400,000 | 2,349,909 | 26.298 | 207.087 |
| 16,000,000 | 5,874,161 | 66.980 | 703.772 |

마지막 16,000,000개에서 66.98초, 최고 메모리 703.77 MB를 관측했다. 먼저 도달한 실험 종료 기준은 시간이었다. 메모리 부족이나 실행 실패가 발생한 것은 아니며, 이 수치를 컴퓨터가 처리할 수 있는 최대 입력 크기로 주장하지 않는다. 사용자 개인이 불편함을 느꼈다는 보고도 아니다.

640만 개의 FM은 이후 별도 실행에서 set과 함께 측정하여 앞의 비교 표에 반영했다. 1,600만 개의 FM은 실행 도중 중단되어 완료 결과가 없으며, 긴 측정 시간 때문에 재실행하지 않기로 했다. 따라서 1,600만 개는 set의 시간 부담을 확인한 추가 실험으로만 사용하고, FM 결과를 외삽하거나 임의로 채우지 않았다.

## 2배 오차가 허용되는 경우

오늘 방문자가 수천 명인지 수십만 명인지 파악하는 대략적인 규모 추정에는 사용할 수 있다. 반면 고유 방문자 수에 따른 과금·정산이나 전일 대비 5% 변화 확인에는 2배 수준의 오차가 부적절하다. 2배 허용 범위는 이번 과제의 검증 기준이며 모든 입력에 대한 확정적인 오차 보장이 아니다.

## 재현과 원시 자료

```bash
python task2_limits.py --sizes 10000,40000,160000,640000
python task2_limits.py --sizes 6400000
python task2_limits.py --exact-only --sizes 6400000,16000000
python test_tasks.py --task 2
```

[원시 측정값](limits.json)의 mode=paired는 비교 실험, mode=exact_only는 추가 경계 탐색이다. 제공 측정기에 환경 기록, 진행 출력, 각 크기 완료 시 저장, 명시적인 exact-only 옵션을 추가했다. 알고리즘과 기본 스트림 생성 방식은 유지했다. 재실행 결과는 누적되므로 이 표를 갱신할 때는 대상 실행을 구분해야 한다.
