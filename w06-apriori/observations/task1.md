# Task 1 — Apriori와 연관 규칙

## 예상과 구현

어떤 쌍의 등장 횟수는 그 구성 항목 각각의 등장 횟수보다 클 수 없다. 따라서 빈발하지 않은 항목이 포함된 쌍은 빈발 쌍일 수 없으며, 첫 통과에서 이를 제거하면 정답을 잃지 않고 두 번째 통과의 계수를 줄일 수 있을 것으로 예상했다.

첫 통과에서 항목별 장바구니 등장 횟수를 세고, 두 번째 통과에서는 살아남은 항목끼리의 쌍만 생성한다. 각 장바구니를 집합으로 처리하므로 같은 항목이 반복돼도 그 장바구니에서는 한 번만 센다. 쌍은 frozenset으로 표현해 순서에 따른 중복을 없앴다. 지지도는 비율이 아닌 양의 정수 등장 횟수다. 두 번 순회해야 하므로 frequent_pairs는 한 번만 소비할 수 있는 iterator를 명시적으로 거부한다. association_rules는 길이를 구할 수 있는 장바구니 컬렉션을 사용한다.

## 손계산과 검증

제공된 7개 장바구니에서 지지도 3을 적용하면 beer·bread·diaper·milk가 각각 5회로 살아남는다. cola 2회와 egg 1회는 쌍을 세기 전에 제외된다. 빈발 쌍은 6개이고 bread–milk와 beer–diaper가 각각 4회, 나머지는 3회다.

diaper→beer의 신뢰도는 4/5=0.8, 향상도는 0.8/(5/7)=1.12이다. beer가 원래 7개 중 5개 장바구니에 있으므로 높은 신뢰도만으로 강한 관계를 주장하기 어렵다. 공식 검증 5개를 모두 통과했고, 중복 항목을 포함한 무작위 작은 데이터 40개에서는 모든 쌍을 직접 센 결과와 정확히 일치했다. 빈 입력도 확인했다.

## 신뢰도는 방향에 따라 다르다

제공 작은 예제의 빈발 항목은 모두 등장 횟수가 5여서 그 쌍들의 양방향 신뢰도가 우연히 같다. 이를 신뢰도가 대칭이라는 증거로 해석하지 않는다. 별도의 네 장바구니 {X,Y}, {X,Y}, {X}, {X}에서는 X→Y=2/4=0.5, Y→X=2/2=1.0이지만 두 방향의 향상도는 모두 1이다. X가 항상 등장하므로 Y→X의 신뢰도 100%도 추가적인 예측 가치를 주지 않는다.

공식 생성 데이터에서는 최고 신뢰도 규칙인 1468→0의 쌍 등장 횟수는 52, 항목 1468은 62회, 항목 0은 13,080회였다. 따라서 1468→0의 신뢰도는 52/62≈83.87%, 반대 방향 0→1468은 52/13,080≈0.398%이다. 1468을 산 사람에게 0을 제안하는 방향이 조건부 비율로는 더 강한 주장이지만, 항목 0 자체의 구매 비율이 65.4%이므로 이 규칙의 향상도는 약 1.282에 그친다.

## 최고 신뢰도 규칙을 믿을 수 있는가?

고정 시드 246, 20,000개 장바구니, 상품 2,000개, 지지도 50에서 찾은 규칙 중 최고는 1468→0이다. 신뢰도 약 83.87%는 전체의 항목 0 구매 비율보다 높지만, 근거는 62개 장바구니 중 52개이고 다수의 규칙 중 최댓값을 고른 결과다. 같은 데이터에서 발견하고 평가했으며 합성 데이터이므로 실제 추천 효과나 인과관계를 입증하지 않는다. 독립된 데이터의 재검증 없이 강한 관계라고 단정하지 않겠다.

## 가능한 쌍과 실제 카운터는 다르다

| 항목 | 개수 |
|---|---:|
| 전체 2,000개 상품의 가능한 쌍 | 1,999,000 |
| 첫 통과 후 빈발 항목 | 1,849 |
| 빈발 항목끼리의 가능한 쌍 | 1,708,476 |
| 두 번째 통과에서 실제 생성한 쌍 카운터 | 820,259 |
| 최종 빈발 쌍 | 6,397 |

전체 쌍에 미리 카운터를 배정하는 방식은 2,000×1,999/2=1,999,000개가 필요하다. Apriori 후의 후보 공간 상한은 1,849×1,848/2=1,708,476개지만, 이 구현은 실제 함께 등장한 쌍에만 카운터를 만든다. 따라서 실제 개수는 820,259개다. 직접 계수하는 방식도 희소 사전을 쓰면 모든 가능한 쌍을 미리 할당할 필요는 없으므로 이 수치들을 같은 종류의 메모리 실측값처럼 비교하지 않는다.

쌍 카운터 수는 정답 수의 약 128배로, 대부분의 계수 대상은 최종 답이 되지 않았다. 이 차이가 이후 지지도 실험과 PCY 개선에서 살펴볼 비용이다. 카운터 개수는 전체 Python RAM 사용량을 뜻하지 않으며, 이번 Task에서는 실행 시간·메모리 한계를 측정하지 않았다.
